16  El diccionario de variables

16.1 Qué vas a poder hacer

Al terminar este capítulo, vas a poder realizar las siguientes acciones.

  1. Vas a poder explicar qué es un diccionario de variables y para qué sirve.

  2. Vas a poder identificar la información que debe documentarse para cada variable.

  3. Vas a poder pedirle a un agente un borrador del diccionario a partir del código.

  4. Vas a poder verificar ese borrador contra el código y contra un archivo de datos real.

  5. Vas a poder completar el diccionario con las decisiones que el código no contiene.

  6. Vas a poder comparar tu proyecto con el checkpoint del final de la Parte III.

16.2 Un número sin contexto permite formular el problema

Imaginá que dentro de tres meses abrís un archivo de datos de tu estudio y encontrás esta celda.

{"efoe_1":3,"efoe_2":4,"efoe_3":1,"efoe_4":0}

¿Qué significa efoe? ¿El 3 es “De acuerdo” o “Ni de acuerdo ni en desacuerdo”? ¿El ítem 3 se suma directamente o se invierte? ¿Cuál es el puntaje máximo posible?

Hoy conocés las respuestas porque acabás de construir el estudio. Dentro de tres meses, probablemente no. Otra persona que quiera revisar o reproducir tu trabajo no las conoce en absoluto. Un agente que lea el archivo en una sesión nueva tampoco.

En el capítulo sobre computadoras viste que un dato necesita contexto para interpretarse: el valor 22 puede ser una edad, un puntaje o una cantidad de respuestas correctas. Este capítulo reúne ese contexto en un documento.

Idea clave

Un diccionario de variables describe cada variable de un estudio: de dónde viene, qué valores puede tomar y cómo se interpretan. Es la documentación que permite entender los datos sin depender de la memoria de quien los recolectó.

16.3 Un diccionario describe cada variable

Un diccionario de variables, también llamado libro de códigos, es un documento que describe todas las variables de un conjunto de datos. Para cada variable suele indicar lo siguiente.

  1. Nombre. Cómo aparece la variable en los datos, por ejemplo anio_carrera.

  2. Origen. Qué pantalla o qué proceso la produce.

  3. Contenido. La pregunta textual o la descripción de lo que registra.

  4. Tipo. Si es numérica, categórica, de texto abierto o de respuesta múltiple, y su nivel de medición.

  5. Valores posibles. Qué valores puede tomar y, si están codificados, qué significa cada código.

  6. Datos faltantes. Si puede quedar sin respuesta y cómo aparece en ese caso.

  7. Notas. Cualquier información necesaria para interpretarla, como un ítem invertido o una regla de puntuación.

En el capítulo sobre Google Forms escribiste una especificación de variables en el README. La especificación describe lo que el estudio debería registrar. El diccionario describe lo que el estudio efectivamente registra. Si ambos coinciden, la implementación cumple la especificación. Si difieren, encontraste algo que revisar.

16.4 El diccionario también describe variables que no pediste

Tu archivo de datos contiene variables que no provienen de ninguna pregunta: participante, pantalla, rt, time_elapsed, trial_index y trial_type. Algunas las agregaste vos. Otras las agrega jsPsych por su cuenta.

Todas deben figurar en el diccionario. Una persona que abra el archivo va a encontrar esas columnas y necesita saber qué significan.

Además, el diccionario debe explicar la organización del archivo. En tu estudio, las respuestas no ocupan columnas propias: aparecen agrupadas en la columna response. Esa particularidad, que estudiaste en el capítulo anterior, también se documenta.

16.5 El diccionario va en su propio archivo

El diccionario de tu estudio va a ser un archivo Markdown llamado diccionario.md, dentro de la carpeta principal del proyecto.

mi-primer-estudio/
├── index.html
├── experiment.js
├── diccionario.md
└── README.md

Podría ser una sección del README, pero un archivo separado tiene ventajas. Se puede compartir junto con los datos sin incluir el resto de la documentación. Además, el README queda breve y enfocado en presentar el proyecto.

16.6 Este capítulo importa para investigar en Psicología

La reproducibilidad, que definiste en el capítulo sobre el ciclo de trabajo, depende de que otra persona pueda comprender tus datos. Muchas revistas científicas y repositorios de datos piden un diccionario de variables junto con los datos. Cuando publiques datos en un repositorio como Zenodo, en la Parte V, el diccionario va a ser parte de lo que publiques.

El diccionario también es una herramienta de verificación. Escribirlo te obliga a revisar cada variable, y en ese proceso suelen aparecer problemas: un nombre de variable repetido, una opción que no coincide con la especificación, una codificación que no esperabas.

16.7 Pedile a Codex un borrador

Extraer la lista de variables de experiment.js es una tarea repetitiva y técnica: consiste en leer cada ensayo y anotar sus nombres, preguntas y opciones. Es el tipo de tarea en la que un agente puede ahorrarte tiempo.

Sin embargo, el código no contiene toda la información del diccionario. No dice cómo se puntúa la escala, ni qué valor numérico registra jsPsych para cada opción, ni cómo tratar un dato faltante en el análisis. Esas son decisiones metodológicas. El agente puede extraer lo que el código dice. No puede saber lo que el código no dice.

Por eso el pedido le indica al agente que marque lo que no puede determinar.

Trabajá con Codex

  1. Iniciá Codex en mi-primer-estudio con permisos Read Only.

  2. Escribí este pedido.

Creá un archivo diccionario.md a partir de lo que define experiment.js.
Usá esta estructura:

# Diccionario de variables

## Organización del archivo de datos
Un párrafo que explique que el archivo tiene una fila por pantalla y que las
respuestas a las preguntas aparecen dentro de la columna response.

## Variables generales
Una tabla con las columnas: Variable | Dónde aparece | Tipo | Valores posibles | Notas.
Incluí participante, pantalla, rt, time_elapsed, trial_index y trial_type.

## Variables de las preguntas
Una tabla con las columnas: Variable | Pantalla | Pregunta | Tipo | Valores posibles | Obligatoria.
Incluí una fila por cada name definido en experiment.js, con la pregunta textual
y las opciones exactas.

Usá solamente información que esté en experiment.js. Si algo no se puede determinar
leyendo el código, escribí PENDIENTE en esa celda. No inventes información.
No modifiques ningún otro archivo.
  1. Revisá la propuesta de cambio. Es un archivo nuevo, así que todas las líneas van a aparecer con +. Leela completa antes de aprobarla.

Sin acceso a Codex: escribí el diccionario con el editor, usando como modelo el archivo proyectos\04-escalas\diccionario.md. No lo copies directamente: completalo leyendo tu propio experiment.js.

16.8 Explicá qué hizo realmente el agente

El agente leyó experiment.js y recorrió los ensayos. Para cada pregunta, extrajo el valor de name, el texto de prompt y las opciones. A partir de esa información armó las tablas con el formato que le indicaste.

Para completar algunas celdas, el agente tuvo que interpretar el código. Por ejemplo, para indicar el tipo de la variable edad tuvo que reconocer que type="number" significa un campo numérico. Para describir rt o time_elapsed tuvo que usar conocimiento general sobre jsPsych, porque esas columnas no aparecen en tu código.

Esas interpretaciones pueden ser correctas o no. Por eso el paso siguiente es la verificación.

16.9 Verificá el borrador contra el código y contra los datos

La verificación del diccionario tiene dos comparaciones. La primera compara el diccionario con el código. La segunda lo compara con un archivo de datos real. La segunda es la más importante: el diccionario describe los datos, y solo los datos muestran lo que realmente se registra.

Realizá esta actividad guiada

  1. Completá el estudio una vez con respuestas conocidas. Anotá tus respuestas mientras lo hacés. Usá el mismo patrón de la escala del capítulo sobre escalas: 3, 4, 1 y 0 en los valores registrados.

  2. Abrí el archivo de datos descargado en una planilla de cálculo.

  3. Abrí diccionario.md en el editor.

  4. Para cada fila de la tabla de variables de las preguntas, comprobá:

    • que el nombre coincida exactamente con el que aparece en los datos;
    • que la pregunta coincida con la de experiment.js;
    • que los valores posibles coincidan con los que registró jsPsych;
    • que la obligatoriedad coincida con el comportamiento del estudio.

  5. Buscá en particular la fila de la escala. ¿Qué valores posibles indica el borrador? ¿Coinciden con los valores 0 a 4 que registró jsPsych?

  6. Buscá las celdas marcadas como PENDIENTE. Anotá qué información falta en cada una.

  7. Anotá toda diferencia que encuentres entre el borrador y los datos.

Un error frecuente en los borradores generados por agentes es describir los valores de una escala Likert como 1 a 5. Muchas escalas se codifican así, y el modelo de lenguaje puede suponerlo. Sin embargo, jsPsych registra valores de 0 a 4. Solo la comparación con un archivo de datos real detecta esa diferencia. Si la encontraste, acabás de observar por qué el informe de un agente, o un documento redactado por él, no reemplaza la verificación.

16.10 Completá el diccionario con las decisiones metodológicas

El borrador describe lo que está en el código. Faltan dos secciones que expresan decisiones: la codificación y puntuación de la escala, y el tratamiento de los datos faltantes. Esa información la aportás vos, a partir de la especificación del capítulo sobre escalas.

Trabajá con Codex

Primero, pedí que se corrijan las diferencias que encontraste. Formulá un pedido por cada diferencia, con el valor correcto. Por ejemplo:

En diccionario.md, en la fila de efoe_1 a efoe_4, reemplazá los valores posibles por
"0 a 4 (ver codificación)". No modifiques ninguna otra parte del archivo.

Después, agregá las secciones finales.

En diccionario.md, agregá al final del archivo este contenido exacto:

## Codificación de la escala ficticia

La escala de organización del estudio es **ficticia y tiene fines didácticos**. No es un instrumento validado.

jsPsych registra la posición de la opción elegida, contando desde 0.

| Opción | Valor registrado |
|:---|:---|
| Totalmente en desacuerdo | 0 |
| En desacuerdo | 1 |
| Ni de acuerdo ni en desacuerdo | 2 |
| De acuerdo | 3 |
| Totalmente de acuerdo | 4 |

El ítem `efoe_3` ("Dejo el estudio para el último momento.") está redactado en sentido inverso. Antes de sumar los ítems hay que invertirlo: el valor invertido es `4 - efoe_3`.

## Datos faltantes

- Las preguntas obligatorias no admiten respuestas vacías.
- Si la persona no escribe un comentario, `comentarios` queda como texto vacío (`""`).
- Si una persona cierra la ventana antes de terminar, en esta versión no se descarga ningún archivo.

No modifiques ninguna otra parte del archivo ni otros archivos.

Finalmente, resolvé las celdas PENDIENTE que queden. Para cada una, decidí el contenido y pedí el cambio con el texto exacto, o editala vos con el editor.

Sin acceso a Codex: agregá las secciones con el editor.

16.13 Revisá algunas situaciones que suelen causar errores

16.13.1 El diccionario describe lo que se pidió, no lo que se registró

Si escribís el diccionario a partir de la especificación en lugar de los datos, podés documentar una variable que nunca se implementó o un valor que el estudio no produce. El diccionario se verifica contra los datos.

16.13.2 Faltan las variables generadas por jsPsych

Columnas como rt o time_elapsed aparecen en los datos aunque no las hayas definido. Si no figuran en el diccionario, una persona que lea los datos no va a saber qué significan.

16.13.3 La codificación no está documentada

Un valor numérico sin su codificación no se puede interpretar. Cada escala necesita su tabla de codificación.

16.13.4 El diccionario quedó desactualizado

Cada vez que modifiques el estudio, revisá si el cambio afecta el diccionario. Agregar una pregunta, cambiar una opción o cambiar un nombre de variable requiere actualizarlo. Incluí esa revisión en tu ciclo de trabajo.

16.13.5 El agente completó una celda PENDIENTE por su cuenta

Si una celda que el código no permite determinar aparece completa, preguntá de dónde salió esa información. Puede ser una suposición razonable o una invención.

16.14 Comprobá lo que comprendiste

Respondé cada pregunta con una oración completa.

  1. ¿Qué es un diccionario de variables?

  2. ¿Qué diferencia existe entre la especificación de variables y el diccionario?

  3. ¿Por qué el diccionario incluye variables como rt o trial_index?

  4. ¿Qué parte del diccionario puede extraer un agente del código y qué parte no?

  5. ¿Por qué el pedido indicaba escribir PENDIENTE en lugar de completar todas las celdas?

  6. ¿Por qué se verifica el diccionario contra un archivo de datos real?

  7. ¿Cuándo hay que actualizar el diccionario?

Consultá una posible respuesta después de resolver la actividad.

  1. Un diccionario de variables es un documento que describe cada variable de un conjunto de datos: su nombre, origen, contenido, tipo, valores posibles, datos faltantes y notas.

  2. La especificación describe lo que el estudio debería registrar, mientras que el diccionario describe lo que efectivamente registra.

  3. Esas columnas aparecen en los datos, y una persona que lea el archivo necesita saber qué significan.

  4. Un agente puede extraer nombres, preguntas y opciones, pero no puede conocer decisiones que el código no contiene, como las reglas de puntuación o el tratamiento de los datos faltantes.

  5. Para evitar que el agente complete con suposiciones o invenciones la información que no puede determinar.

  6. Porque solo los datos muestran lo que el estudio realmente registra, como la codificación de 0 a 4 de la escala.

  7. Hay que actualizarlo cada vez que un cambio en el estudio afecte alguna variable.

16.15 Qué aprendiste en este capítulo

Un diccionario de variables describe cada variable de un conjunto de datos, incluidas las que agrega jsPsych por su cuenta. Documenta nombre, origen, contenido, tipo, valores posibles, datos faltantes y notas, y explica la organización del archivo.

La especificación describe lo que el estudio debería registrar. El diccionario describe lo que efectivamente registra. Compararlos es una forma de verificar la implementación.

Un agente puede producir un borrador a partir del código, pero solo puede describir lo que el código contiene. Las decisiones metodológicas, como la codificación y la puntuación de una escala, las aporta el investigador. El borrador se verifica contra un archivo de datos real.

Tu proyecto coincide ahora con el checkpoint 04-escalas.

16.16 Cerrá la Parte III

Con este capítulo termina la Parte III. Empezaste analizando qué hace Google Forms y terminaste con un estudio que reproduce un formulario completo con jsPsych.

Tu estudio tiene bienvenida, consentimiento, cuestionario sociodemográfico con validaciones, una escala ficticia y cierre. Registra un identificador de participante, etiqueta cada pantalla y descarga los datos. Además, está documentado en un diccionario de variables.

En el camino viste dónde queda escrita cada decisión: el texto de una pregunta en prompt, el nombre de una variable en name, una restricción en los atributos de un campo, la obligatoriedad en required, el orden en la línea de tiempo y el guardado en on_finish.

16.17 Resolvé un desafío breve

Imaginá que otra persona del equipo agrega al estudio esta pregunta, sin avisarte.

const pregunta_trabajo = {
  type: jsPsychSurveyMultiChoice,
  questions: [
    { prompt: "¿Trabajás además de estudiar?", name: "trabaja", options: ["Sí", "No"], required: false }
  ],
  button_label: "Continuar",
  data: { pantalla: "trabajo" }
};

  1. Escribí la fila del diccionario para la variable trabaja.

  2. Indicá qué valor quedaría registrado si una persona no responde. Para averiguarlo, podés agregar la pregunta a una copia de tu proyecto y probarla.

  3. Agregá a la sección de datos faltantes una línea que documente ese caso.

  4. Indicá qué otra parte del diccionario cambiaría. Pensá en la cantidad de filas por participante y en los valores posibles de pantalla.

En la Parte IV vas a incorporar a tu encuesta recursos que Google Forms no ofrece o resuelve mal: el orden aleatorio de los ítems, la lógica condicional, los controles de atención y el análisis de los tiempos de respuesta.
